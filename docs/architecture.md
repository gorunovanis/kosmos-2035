# Архитектура расчёта и снабжения

Один расчётный контур (`src/kosmo`) обслуживает интерфейс, командную строку, тесты и выгрузки. Любое число на экране прослеживается до входов: **данные организатора → решения команды → сценарий → дневной баланс → платежи → проверки → сравнение**.

## 1. Схема потоков

```
CASE_INPUT (data/case: demand.csv, supply_sources.csv, storage_options.csv, investment_options.csv, constraints.csv, base.yaml, mandatory_stress.yaml)
        │
TEAM_DECISION (configs/plans/*.json: резервы по годам, отборы по годам или окнам, инвестиции с датами, политика запаса, роль Emergency)
        │                                        TEAM_ASSUMPTION (configs/assumptions.yaml: A1–A14)
        ▼                                                 │
 load_case / load_plan / validate  ──►  apply_scenario (BASE, MANDATORY_STRESS, LOW/HIGH, TEAM_*, гео-событие на копии)
        │
        ▼
 simulate (по дням, 2034 подготовительный + 2035–2040): заказ → lead time → поставка → потери на оборот → запас → выдача (критический сначала) → дефицит
        │
        ▼
 costs: закупка = цена × max(отбор, TOP × резерв периода); резерв = тариф × резерв × доля года; хранение = 0,72 × средний дневной запас; OPEX с даты ввода; CAPEX по датам; дисконт
        │
        ▼
 check_constraints: сервис, резерв 45 дн, CAPEX 1 800/2 800, потери ≤ 2 % в стрессе, серия Emergency, мощность, резерв мощности, ёмкость, сроки
        │
        ├──► export (CSV, XLSX, meta.json с хэшем чисел) ──► results/
        ├──► compare (планы × сценарии, цена защиты) ──► страница «Сценарии и сравнение», comparison.xlsx
        ├──► sensitivity (торнадо, обратный стресс) ──► страница «Чувствительность»
        ├──► risks (реестр как сценарии, меры, остаточный риск), stakeholders, mcda-профили ──► страница «Риски и стороны»
        └──► planner (правило заполнения объёмов; результат всегда перепроверяется ядром)
```

## 3. Концептуальная модель и реализация

Концептуально узел — резервуар с дневным притоком от каналов и дневным оттоком спроса. Контракты дают право на приток (резерв мощности) и обязательство платить минимум (take-or-pay). Инвестиции меняют набор каналов и режим резервуара с заданных дат. Ограничения проверяются на каждом дне (ёмкость, неотрицательность) и по годам (сервис, резерв, CAPEX, потери, серия Emergency).

Реализация — чистый Python без внешних сервисов: `run()` за один проход по дням строит годовые агрегаты, затем считает платежи и проверки. Все структуры сериализуются в CSV/XLSX/JSON; интерфейс на Streamlit вызывает те же функции, что и CLI и тесты.

## 4. Формат плана (TEAM_DECISION)

```json
{"plan_id": "...", "scenario_id": "BASE",
 "decisions": {
   "capacity_reservations": [{"source_id": "A", "year": 2035, "reserved_t_per_year": 190}],
   "supply_orders": [{"source_id": "A", "year": 2035, "volume_t": 133, "role": "planned"},
                     {"source_id": "B", "volume_t": 12.98, "start": "2034-11-18", "end": "2034-12-31", "role": "preparatory", "decided_on": "2034-07-19"}],
   "investments": [{"investment_id": "EARTH_NEW", "option_fee_date": "2035-01-15", "exercise_date": "2035-07-01", "lead_months": 24},
                   {"investment_id": "ZBO", "decision_date": "2036-01-01", "lead_months": 0}],
   "inventory_policy": {"reserve_days": 45, "reserve_mode": "physical"},
   "emergency_policy": {"role": "insurance", "planned_years": []}}}
```
Совместим с `plan.schema.json` организатора (обязательные поля присутствуют, дополнительные разрешены).

## 5. Формат нарушения

`rule_id · scenario · period · actual · limit · excess · unit · cause · severity`, например
`CAPACITY_EXCEEDED · BASE · 2035 · 12 · 10 · 2 · t/year · reserved capacity of Source-X exceeds source capacity · hard`.
