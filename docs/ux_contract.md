# Контракт интерфейса и расчётного ядра (для UX MVP)

Версия 19.09, по коду `src/kosmo` (ядро сверено с независимым расчётом). Всё ниже уже реализовано в ядре, интерфейс только показывает и редактирует.

## 0. Нужна ли LLM под капотом
Нет. Постановка: «чат-бот должен запускать расчёты, а не заменять их генерацией; роль ИИ отделяется от рассчитанных показателей». Баллов за ИИ нет, риск расхождения чисел есть. Все числа на экране идут из ядра. Пояснения «почему нарушение» формируются шаблонами из чисел. Ollama/qwen из старого MVP убираем.

## 1. Что вводит оператор (входные параметры)
Условия организатора (спрос, 5 каналов, хранилище, инвестиции, лимиты, стресс) показываются **только для чтения**. Менять их можно только на копии набора (Source-X, 2041).

| Блок | Поля | Диапазон / формат |
|---|---|---|
| Сценарий | выбор: BASE, MANDATORY_STRESS, LOW_DEMAND, HIGH_DEMAND, TEAM_* (свои), гео-событие на копии | список |
| Резерв мощности | по каналу A Earth-Core, B Earth-Flex, C Earth-New, E Emergency и по году 2035–2040: `reserved_t_per_year` | 0 … мощность канала (190/110/130/80); D Lunar-ISRU без резервирования |
| Заказы (отбор) | по каналу и году: `volume_t`; опционально окно `start`/`end` (частичный год), `role` planned / reactive / preparatory, `decided_on` (дата решения, по умолчанию = начало окна − lead time), `cause` (текст для реактивных) | т, ≥0; даты YYYY-MM-DD без 29 февраля |
| Инвестиции | Earth-New: дата покупки права (90), дата реализации (270), lead 18–24 мес, дата ввода; ZBO: дата решения (не ранее 01.01.2036), lead мес; Lunar-ISRU: дата финансирования (до 31.12.2037 для ввода в 2038) | даты, месяцы |
| Начальный запас | подготовительный заказ 2034: канал, объём брутто, окно поставки, дата решения | по умолчанию B, 12,98 т брутто = 12,4 т нетто |
| Политика запаса | резерв 45 дней (условие кейса, показать), режим physical, целевые остатки на конец года (если используем автоподбор) | дни, т |
| Emergency | роль insurance (только резерв) или planned c перечнем лет | ≤ 2 лет подряд как база |
| Допущения (глобальные) | ставка дисконта 7 %, год приведения 2035, порог «Emergency как база» 10 %, календарь 365 дней | панель «Допущения», редактируемые с пометкой TEAM_ASSUMPTION |
| Гео-событие (бонус) | название, затронутые каналы, составляющая цены (variable_price / reservation_rate / capacity), годы с… по…, множитель или диапазон, основание | работает на копии данных, кнопка «вернуть контрольные цены» |

Кнопка «Заполнить объёмы автоматически» (планировщик) не обязательна: оператор может ввести всё руками.

## 2. Что возвращает расчёт
Один прогон = план × сценарий. Возвращает:

1. **Баланс по годам** (`yearly_balance`): спрос total/critical, требуемый резерв на 1 января, запас на начало, заказано, доставлено, потери, доля потерь, served total/critical, дефицит total/critical, запас на конец, SL total/critical, средний запас, пик запаса, дата первого дефицита, дней с дефицитом; расходы: закупка, резервирование, хранение, OPEX ZBO, OPEX ISRU, CAPEX года, CAPEX накопленный, расходы подготовительного периода, итого, коэффициент дисконта, приведённые расходы, стоимость тонны served, PV на тонну.
2. **График по каналам** (`source_schedule`): по каналу и году: резерв, доля периода, заказано, доставлено, минимум take-or-pay, оплаченный объём, оплачено сверх отбора, цена, закупочный платёж, ставка и платёж за резерв.
3. **Дневной след запаса** (`inventory_trace`): дата, запас на начало, поступление план/факт, потери, запас после поступления, выдача критическим/прочим, дефицит, запас на конец, ёмкость, режим хранилища.
4. **Проверки** (`constraint_checks`): все правила с PASS/FAIL: правило, период, факт, знак, порог, запас до порога, единица, статус, тяжесть, причина.
5. **Нарушения** (`violations`): только FAIL.
6. **Итоги горизонта**: расходы без дисконта и с дисконтом, served, дефицит, CAPEX, конечный запас, стоимость тонны, минимальные SL.
7. **Мета**: сценарий и список его изменений, даты ввода ZBO/New/ISRU, события CAPEX, допущения, хэш чисел, версия кода, признак исполнимости.

## 3. Ключевые метрики на экране результата и в сравнении
1. **Приведённые расходы 2035–2040** (PV при 7 %) и расходы без дисконта, млн.
2. **Сервис**: минимальный годовой SL total и SL critical; дефицит в тоннах (в стрессе).
3. **Исполнимость**: число жёстких нарушений (0 = план исполним) и запасы до порогов: резерв на 1 января, CAPEX до лимитов 1 800 / 2 800.
4. **Стоимость тонны обслуженного спроса**, млн/т.
5. **Цена защиты и гибкость**: расходы подготовленного стресс-плана минус базовые; незанятая мощность Flex/Emergency; CAPEX-экспозиция.

Пример текущих чисел (PV, млн): BASE — S2 8 998, S1 9 342, S3 9 631, S0 9 733; подготовленный стресс — S1 10 955, S3 11 134, S2 11 378; S1 с реакцией после наблюдения стресса — 11 115.

## 4. Статусы, ошибки, ограничения
**Статус плана:** `FEASIBLE` (нет жёстких нарушений) · `INFEASIBLE` (есть жёсткие) · в стрессе дополнительно `REFERENCE_BREACH` (сервис ниже ориентира 97/99 %, тяжесть reference, не жёсткое).

**Ошибки ввода (до расчёта):** `INVALID_INPUT` (нет поля, не число, плохая дата, 29 февраля), `NEGATIVE_VALUE`, `UNKNOWN_SOURCE`, `UNKNOWN_SCENARIO`, `FILE_NOT_FOUND`. Показывать рядом с полем.

**Нарушения (после расчёта), формат `правило · период · факт · порог · превышение · единица · причина`:**
`BASE_TOTAL_SERVICE` ≥ 0,97 · `BASE_CRITICAL_SERVICE` ≥ 0,99 · `TOTAL_SERVICE_REFERENCE` / `CRITICAL_SERVICE_REFERENCE` (стресс) · `RESERVE_45D` (запас на 1 января ≥ 45 дней спроса) · `CAPEX_2037` ≤ 1 800 · `CAPEX_2040` ≤ 2 800 · `STRESS_LOSS_LIMIT` потери/оборот ≤ 2 % с 2038 в стрессе · `EMERGENCY_BASE_STREAK` ≤ 2 лет · `CAPACITY_EXCEEDED` · `ORDER_EXCEEDS_RESERVATION` · `STORAGE_OVERFLOW` (70 / 120 т) · `LEAD_TIME_VIOLATION` · `SOURCE_NOT_AVAILABLE` · `INVESTMENT_NOT_FINANCED` · `INVESTMENT_NOT_AVAILABLE`.

**Состояние «нет решения».** Система ничего не чинит сама. Экран показывает: статус INFEASIBLE, таблицу нарушений с годом, величиной и причиной, и подсказку по рычагу для каждого правила (например, `RESERVE_45D 2039: 1,95 т против 45,37 т` → увеличить отбор Flex в 2038 или подготовить план под стресс; `STRESS_LOSS_LIMIT 2038: 4,5 % против 2 %` → ZBO до 2038; `CAPEX_2037: 1 790 против 1 800` → сдвинуть инвестицию). Отдельно предупреждения автоподбора: «требуемый остаток превышает ёмкость», «потребность не покрывается разрешёнными каналами».

## 5. Выгрузка
Папка прогона `results/<план>_<сценарий>/`: `yearly_balance.csv`, `source_schedule.csv`, `financial_breakdown.csv`, `constraint_checks.csv`, `violations.csv`, `inventory_trace.csv`, `assumptions.csv`, `risk_register.csv`, `meta.json`, `plan.json` (для повторного открытия), `export.xlsx` (все листы плюс лист `meta`: сценарий, план, единицы, допущения, даты ввода, хэш чисел, версия кода). Сравнение: `comparison.csv/xlsx` по планам и сценариям. CSV в UTF-8, разделитель запятая, десятичная точка, 6 знаков. План сохраняется и открывается как JSON по схеме организатора `plan.schema.json`. Числа в UI, CSV и XLSX идут из одного прогона, хэш совпадает.

## 6. User flow и экраны MVP
Ввод параметров → проверка ввода → расчёт → проверки ограничений → сравнение сценариев/планов → выбор → сохранение плана → выгрузка. Автоматические шаги: валидация, расчёт, проверки, хэш. Точки проверки: после ввода (ошибки полей), после расчёта (нарушения), перед выгрузкой (статус).
Экраны: 1) План и контракты (ввод) · 2) Результаты (таблица по годам, KPI, нарушения, состояние «нет решения») · 3) Сравнение (BASE / STRESS / стратегии) · 4) Сохранение и выгрузка. Плюс панели «Допущения» и «Геополитика».
